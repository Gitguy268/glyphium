# ADR 0001: terminal-state core

Status: **Proposed**. The gates point to libghostty-vt. It adds Zig to the toolchain, so the user signs off before M2 builds on it.
Date: 2026-10-26. Runs: Apple M4, macOS 27.0.1, AC power, Rust 1.99.1, Zig 0.17.0, Playwright Chromium (headless).
Raw data: `bench/results/2026-10-25-bakeoff/`. Code: `bench/bakeoff/`, `bench/web/run-bakeoff.mjs`.

## Candidates and pins

| Core | Pin | How it is used |
| --- | --- | --- |
| libghostty-vt | ghostty-org/ghostty `cec8b92f1ecd176a20a56aa405021e7ae991b996` (1.3.2-dev) | C API through bindgen; static `libghostty-vt.a`, native (ReleaseFast) and wasm32-freestanding (ReleaseSmall) |
| alacritty_terminal | crates.io 0.26.0, vte 0.15.0 | Vendored; wasm32 patch (OS-only modules gated). vte patched by one line (see below) |
| wezterm-term | wezterm/wezterm `e2a98e1b8af156988ad0ac778658ac27b60a55fb` | Vendored with termwiz and wezterm-escape-parser; wasm32 patches; replies written synchronously |

All three sit behind one `Core` trait (`write`, `snapshot`). A snapshot holds:
- cells: grapheme text, width, colours, attributes, hyperlink;
- row wrap flags;
- cursor position and visibility;
- the active screen and the title;
- the last 1000 scrollback rows;
- every reply byte the core has sent.

Terminal size 120x40 with 5000 lines of scrollback, matching the xterm.js baseline.

## Gate results

### 1. Chunk-invariance (the pass/fail gate)

Each core is compared only with itself. Snapshots are hashed at 25/50/75/100% of each fixture, and those offsets are always chunk boundaries. Two tiers:
- **Exhaustive:** `edge-cases` (3.4 KB of parser edge cases) is split at every byte offset (3,425 runs), plus the sampled set.
- **Sampled:** the five large fixtures (2.4–11.4 MB) are fed in fixed chunks of 1, 2, 3, 7, 13 and 4096 bytes, and in four seeded random chunkings.

Every run is compared with the same fixture written in one call.

| Core | edge-cases (3,435 runs) | 5 large fixtures (10 runs each) | with mode 2027 on |
| --- | --- | --- | --- |
| libghostty-vt | **pass** | **pass** | **pass** |
| alacritty_terminal + vte 0.15.0 as released | 6 failures | unicode-mix: 7/10 fail | — |
| alacritty_terminal + vte one-line fix | **pass** | **pass** | pass (no clustering) |
| wezterm-term | 78 failures | unicode-mix: 10/10 fail | 78 failures |

The failures, and their causes:
- **vte 0.15.0 (alacritty):** when a write ends inside a UTF-8 character, the parser prints that character once the next write arrives, but also consumes any further valid bytes it had copied into its 4-byte buffer. So `é` followed by a space loses the space.
  - Upstream: alacritty/vte#159 describes this and was closed on 2026-09-01. The fix, PR #162, was closed unmerged on 2026-10-18, and master still has the bug.
  - Our fix is one line: `c.len_utf8() - old_bytes` in `third_party/vte/src/lib.rs`.
  - Byte-at-a-time feeding hides the bug; only splits that leave more bytes in the same chunk show it.
- **wezterm-term:** grapheme clusters join only within one `advance_bytes` call.
  - All 78 failing split points are inside a cluster: ZWJ emoji, the Devanagari conjunct क्ष, or a combining mark after a pending wrap. Splits inside a single UTF-8 character pass.
  - Real PTY reads split anywhere, so in practice ZWJ emoji break at random.

A harness bug found on the way: upstream wezterm-term delivers replies on a background thread. Before vendoring it with synchronous replies, 367 of its 445 edge-case failures were that race, not the parser.

### 2. Real WASM build in a Web Worker

All three build for `wasm32-unknown-unknown` from the same adapter code and run in a module Web Worker in headless Chromium. In all 18 fixture × core cases, the checkpoint hashes are **byte-identical to the native run** (`wasm-worker.json`, `native-hashes-fixed-4096.json`).

What each core needed:
- **libghostty-vt:** Zig's wasm32 static library links straight into the Rust module. Its only host needs are libm and `strlen`, which Rust supplies. One adapter setting was required: Ghostty's default scrollback *byte* limit is reached before the line limit, after about 565 lines of ascii-flood, and its page granularity differs between 32- and 64-bit builds. The adapter removes the byte limit so the 5000-line limit governs.
- **alacritty_terminal:** 13 lines gating PTY and event-loop modules. A custom vte `Timeout` is needed, because the default calls `Instant::now()`, which panics on wasm32.
- **wezterm-term:** four vendored crates, rewritten manifests, the thread removal, and a C compiler with a wasm32 backend (Homebrew LLVM; Apple clang has none) for `psm`, which comes in through pest.

### 3. Size (`wasm-sizes.tsv`, `native-sizes.tsv`)

Each wasm build contains one core plus the same adapter, sha2 and wasm-bindgen glue. Settings: opt-level z, LTO, panic=abort, then `wasm-opt -Oz`.

| Core | wasm after -Oz | gzip -9 | native stripped binary, minus the 320 KB no-core runner |
| --- | --- | --- | --- |
| libghostty-vt | 475 KB | 154 KB | +1,180 KB (Zig ReleaseFast, no cross-language LTO) |
| alacritty_terminal | 135 KB | 55 KB | +100 KB |
| wezterm-term | 2,110 KB | 812 KB | +1,911 KB |

Notes on the table:
- Ghostty's standalone `ghostty-vt.wasm` exports the whole C API: 863 KB (292 KB gzip). Its interactive feature set (`-all,+render-state,+input-encode,+selection,+color`) is 668 KB (203 KB gzip). That set leaves out the grid-ref API this adapter uses, so a renderer on it would read cells through the render-state API instead.
- wezterm-term requires termwiz's `use_image`, which pulls in image decoders (avif/rav1e, png, tiff, exr…). At this commit it cannot be built without them unless its code is changed.

### 4. Throughput (`throughput-native-4096.json`; wasm in `wasm-worker.json`)

Medians in MB/s. Native: 10 trials after 2 warmups, 4 KiB chunks, core order rotated each round. Wasm: 10 trials in a Web Worker. Only the write calls are timed.

The machine was not idle: load average was about 5 from other sessions. Treat these as relative numbers and re-run on an idle machine before quoting them elsewhere.

| Fixture | ghostty native | alacritty native | wezterm native | ghostty wasm | alacritty wasm | wezterm wasm |
| --- | --- | --- | --- | --- | --- | --- |
| ascii-flood | 829 | 213 | 54 | 874 | 147 | 26 |
| sgr-flood (truecolor) | 187 | 197 | 55 | 127 | 135 | 32 |
| unicode-mix | 144 | 141 | 64 | 117 | 132 | 39 |
| long-lines | 1,102 | 226 | 52 | 1,151 | 155 | 28 |
| tui-redraw | 198 | 190 | 31 | 138 | 145 | 18 |

For scale, xterm.js 6.0.0 on the main thread measured 25 MB/s on ascii-flood and 3.4–3.6 MB/s on sgr-flood (M0 baseline). That includes xterm's buffer updates but not rendering, so the two numbers are not the same measurement.

### 5. Call overhead (Rust↔Zig FFI)

Shrinking writes from 4 KiB to 1 byte on sgr-flood adds per call:
- libghostty-vt: 8.8 ns
- alacritty: 4.0 ns
- wezterm: 11.4 ns

Ghostty is within 4% of its 4 KiB throughput at 256-byte chunks. FFI cost is negligible at real PTY read sizes.

### 6. Unicode (`width-probe.json`; report only, not a gate)

Columns each core gives one cluster on an empty line:
- **wezterm-term** clusters by default (ZWJ family = 2) but gives VS16 `❤️` width 1.
- **alacritty_terminal** does no grapheme clustering: the 4-person family is 8 columns, and skin-tone and ZWJ sequences split.
- **libghostty-vt**, with defaults, behaves like alacritty. With mode 2027 (grapheme clustering, which the Ghostty app enables) it clusters every probe correctly, and it is the only core that gives `❤️` width 2. It stays chunk-invariant with mode 2027 on.

Other observed differences:
- CAN inside an OSC title: alacritty and wezterm still apply the title; Ghostty discards it.
- alacritty pushes the screen into scrollback on `ESC[2J`; the others don't.
- Different DA1/DA2 replies.

### 7. vttest

**Not run.** vttest is interactive (menu-driven), needs a PTY and is not installed. This moves to M2, where the plan already requires vttest results, driven through the M3 PTY layer.

### 8. API stability and toolchain cost

- **libghostty-vt:**
  - `vt.h` says the API "is not yet stable and is definitely going to change", and that applies to all 216 `GHOSTTY_API` functions. Mitigations: pin a commit; keep all FFI in one module; regenerate bindings with bindgen.
  - Needs Zig 0.17.0: a 419 MB unpack, and about 10 minutes for the first native build on this M4. The wasm builds were not timed.
  - Windows CI with Zig is **not verified here**; check it before M7.
  - bindgen needs libclang (Xcode CLT here).
- **alacritty_terminal:** pure Rust and semver-versioned on crates.io. Carries a vte patch until upstream merges a fix.
- **wezterm-term:** not published on crates.io; git dependency only. Needs four vendored crates and a wasm32 C compiler.

## Decision

**Proposed: libghostty-vt** as Glyphium's terminal-state core, used through the C API from Rust natively and linked into the Rust wasm module for the browser.

Why:
- It is the only core that passed every chunk-invariance run as released.
- Its native and wasm states are identical.
- It is as fast as alacritty on styled and Unicode-heavy output and 4–5× faster on plain text.
- Its grapheme clustering (mode 2027) is correct and chunk-invariant.

Its costs:
- Zig in the toolchain;
- an API marked unstable;
- `unsafe` FFI glue;
- about 3.5× alacritty's wasm size (154 KB vs 55 KB gzip).

**Runner-up: alacritty_terminal with the vte fix.** It is smallest and pure Rust. Choosing it means writing and maintaining grapheme clustering ourselves, and carrying the vte patch.

**Rejected: wezterm-term.** It fails chunk-invariance on grapheme clusters, its wasm is 2.1 MB, it is 3–6× slower than alacritty, it has no crates.io release, and its patch surface is the largest.
